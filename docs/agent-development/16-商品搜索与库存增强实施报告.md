## 3. 核心实现与调用链

```text
已有前端聊天入口 → 现有 Agent / LangGraph
  → 商品事实判定 → SEARCH_PRODUCTS 或 GET_PRODUCT_DETAIL
  → 原 MCP Server / 工具服务
  → ProductService
      搜索：ES 关键词 + 向量 → RRF IDs；必要时 Java 关键词/分类/推荐候选
      详情：指定 productId
  → Gateway 既有 /internal/product/**
  → ProductAgentQueryService.queryBatch
      → 商品库批量商品、SKU、规格查询
      → StockFeignClient.queryBatch → 库存服务 selectBatch
  → 完整事实结果 / MCP Wire
  → 服务端确定性文案、商品卡片、最终消息及记忆
```

ES 只提供召回 ID 与顺序，不作为名称、价格、SKU、状态、库存的最终来源。回源时丢弃不存在或非明确在售的搜索候选；详情可明确返回下架/删除状态。ES 查询抛异常或召回为空时，仍可走 Java 关键词候选；产品查询失败不会当成库存零或搜索无结果。

搜索结果为热销/浏览兜底时明确标为另荐，不能当作原关键词命中。推荐、分类、Java 关键词与 ES 路径均经过同一个事实聚合入口。远程 MCP 搜索后不会再执行一遍本地搜索/Embedding。

### 批量库存及兼容性

- queryBatch 商品 ID 数量上限 50，去重；商品、SKU、规格各一次批量 Mapper 查询。
- 库存每批最多 200 个复合键，RPC/SQL 按批执行，而非每 SKU 一个请求；SKU 不截断，不用部分库存冒充完整总库存。
- 严格校验库存 ResponseVO 的 status、code、data、复合键与重复行；异常、无响应、空 data、键不符均不会产生真实库存值。
- 库存行不存在时返回缺失结果，由商品层标 MISSING、stock=null；记录存在且值为 0 才表示真实零库存。null、负值为 INVALID_RESPONSE。
- 仅全部 SKU 库存已知且列表非空时汇总 totalStock，否则 null；SKU 级查询状态始终保留。
- 未修改旧 getStock/getAvailable 的缺行补零契约及 set/change/lock 等交易入口，原业务继续使用原方法。
- SKU 唯一键仍为 `(productId, propertyValueIdHash)`；skuId 为该商品内真实 hash，不虚构独立数据库 SKU 数字 ID。

## 4. 接口结构

新增请求：

```text
POST /internal/product/agent/queryBatch
{"productIds":["<商品ID>"]}

POST /internal/stock/queryBatch
{"items":[{"productId":"<商品ID>","propertyValueIdHash":"<SKU hash>"}]}
```

均沿用既有内部 Token 认证；库存经 Product 的既有 Feign 发现路径访问，不新增 Gateway 库存路由。

商品 Java ResponseVO 外层不变，data.schemaVersion=2，包含 queryStatus、queryTime、products。字段如下：

| 层级 | 字段及含义 |
| --- | --- |
| 商品 | productId、productName、status 原始值、productStatus、minPrice/maxPrice、priceStatus、cover/categoryId/totalSale/productDesc/description |
| SKU | skuId/propertyValueIdHash、productId、propertyValueIds、skuName、specifications、price/priceStatus、stock/stockQueryStatus、availability、stockObservedAt |
| 商品库存 | skuComplete、totalStock、stockQueryStatus、availability |
| 来源/时点 | sources.product/price/stock、productObservedAt、外层 queryTime；库存失败时 stockObservedAt 仅代表查询尝试时点，不能证明取得有效库存 |

商品状态：ON_SALE、OFF_SHELF、DELETED、UNKNOWN、NOT_FOUND。SKU 库存查询：SUCCESS、MISSING、UNAVAILABLE、INVALID_RESPONSE。可用性：IN_STOCK、OUT_OF_STOCK、UNKNOWN、NOT_SALEABLE。

MCP `ToolInvokeResult` 的 productQuery 外层含 schemaVersion=2、queryStatus（SUCCESS / NOT_FOUND / SERVICE_ERROR）、queryTime、retrievalSource、products、message。传输层和商品卡片为 camelCase，Python 商品行内部为 snake_case。数字未知为 null；有效价格保留可精确表达的字符串，不用缺失默认值补 0.00。

Java getDetail 仍支持旧详情基本字段和不存在 data=null；新增事实工具主要走 queryBatch，以取得明确的逐 ID NOT_FOUND。搜索工具未找到匹配但返回另荐商品时会说明另荐；只有完全无结果时外层为 NOT_FOUND。

## 5. Agent 可信回答与流式边界

- `agent_loop_node` 在绑定/调用商品回合的 LLM 前，按现有商品意图及服务端商品事实规则执行必要读工具；不依赖模型自愿选择工具，也不依赖 force_mcp_on_llm_skip 开关。
- 有明确咨询商品 ID 时优先详情，搜索/找类似按搜索；订单、退款等已识别业务意图保留原路径。
- `stream_llm_turn` 对商品事实请求不发送未经验证的模型 delta。`finalize_agent_response` 使用 productQuery 确定性生成名称、价格、SKU、库存及失败提示；即使没有必要工具结果，也不会采用模型补出的库存。
- 普通闲聊继续使用原 astream/push_chunk，已有两段流式输出的 Mock 测试验证其保留。
- `tools_node` 收到商品结果后直接收束，避免再用模型改写关键事实或重复查详情。`post_turn_node` 将同一可信结果写入记忆输入，防止旧 chunks 污染下一回合。
- 未知库存明确说明服务不可用、库存行缺失或响应异常；库存为零明确显示缺货。查询时点库存不是库存锁定或下单承诺。

服务端规则仍是有限的中文意图/关键词规则，不等于已经验证任意语言、任意隐晦指代均可准确路由；这是后续语料验收范围，不能把本轮 Mock 结果扩展成全语言正确性证明。
