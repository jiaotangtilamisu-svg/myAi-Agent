## 三、数据结构与一致性

### 1. 四张独立表

| 表 | 主要字段和约束 |
|---|---|
| `aftersales_case` | case_id、user_id、order_id、source_message_id、request_hash、state、version、plan_version、risk、diagnosis_json、创建/更新时间；唯一 `(user_id, source_message_id)` |
| `aftersales_plan` | `(case_id, version)` 主键；risk、content_json、创建时间；保存方案理由、规范化建议、政策证据及用户补充说明 |
| `aftersales_manual_task` | task_id、case_id、plan_version、attempt、state、handler、result_note、领取/结束时间；唯一 `(case_id, plan_version, attempt)` |
| `aftersales_audit` | event_id、case_id、case_version、plan_version、request_id、request_hash、actor_type/id、action、from/to_state、note、时间；唯一案件版本及唯一 `(case_id, request_id)` |

不修改原订单、退款或 FAQ 表，没有数据清空、原表重建或启动自动迁移。方案与审计提供追加接口，不提供任意覆盖/删除接口。

### 2. 事务、幂等、并发

- 创建使用“当前用户 + 诊断消息 ID”幂等，不把同一订单的所有不同问题强行合并。相同来源、相同规范化诊断重试返回同一案件；相同来源内容变化则拒绝覆盖。
- 案件、初始方案和 CREATE 审计同一事务提交。创建失败不留下半个案件。
- 每次状态命令必须携带 UUID requestId 和 expectedVersion。服务先验证角色与案件权限，再使用 `SELECT ... FOR UPDATE` 串行化同一案件操作。
- 同时使用 `UPDATE ... WHERE version=expected` 防止版本冲突；更新失败整体回滚。
- 已处理请求号绑定动作、版本、说明和操作者，完全相同的重试标记 `replayed=true`，不重复创建任务或写审计。修改内容/操作者后复用请求号会被拒绝。
- 命令重放返回当前案件快照，并附原命令 `appliedVersion`；不谎称又执行一次。
- 状态、方案、人工任务和审计在同一数据库事务内提交。审计失败会使状态和任务一起回滚，测试已实际验证。
- 当前采用本地事务和数据库任务队列式查询，不新增 RabbitMQ 消费者或自动任务执行器；前端消息继续复用现有 Agent 消息/推送机制。

## 四、方案与风险

复用第 18 阶段结构化诊断保存订单事实、物流事实、政策文档名称/版本/章节/来源及诊断理由。方案使用服务端固定建议代码和标题，不直接把模型生成的“自动退款”文案作为执行指令。

LOW 风险必须同时满足：普通售后咨询、当前诊断 NOT_OBSERVED、政策 SUCCESS，且建议全部属于等待、联系承运方/商家、补充说明白名单。其他情况均 HIGH，包括支付、退款、质量、冲突、政策缺失或证据不足。请求中的 risk/approvalRequired/admin 字段不能降低风险或获取审批权。

重新提交时增加 plan_version，保留原方案和政策快照，另存用户补充说明；风险不降低，并重新要求用户确认。当前重新提交是补充说明和再次审核，不会悄悄替换旧诊断/旧政策快照。

## 五、状态流转

```text
创建：AWAITING_USER
  用户确认 LOW  → MANUAL_PENDING
  用户确认 HIGH → ADMIN_REVIEW

ADMIN_REVIEW
  管理员通过 → MANUAL_PENDING
  管理员驳回 → REJECTED

REJECTED
  用户补充并重新提交 → 新方案版本 / AWAITING_USER
  用户或管理员归档   → ARCHIVED

MANUAL_PENDING
  管理员领取 → IN_PROGRESS

IN_PROGRESS
  当前领取人提交成功 → RESOLVED
  当前领取人提交失败及原因 → PROCESSING_FAILED

PROCESSING_FAILED
  管理员填写说明并重试 → 新任务 attempt / MANUAL_PENDING

RESOLVED
  用户或管理员归档 → ARCHIVED
```

禁止从等待用户阶段直接批准、处理成功或归档；管理员不能代替用户确认方案；其他处理人不能替当前领取人提交结果。失败重试保留旧任务及失败原因，不覆盖历史。

## 六、接口设计

沿用项目 POST + ResponseVO 风格。客户端需要同时检查 `status/code`，不能只凭 HTTP 200 判断成功；原全局异常处理也可能把无映射请求包装为业务错误。

### 用户入口

`POST /api/agent/aftersales/cases`：表单 `messageId`。服务按当前登录用户读取 `agent_message`，必须本人、已完成，且 biz_data 为第 18 阶段诊断。客户端不能直接提交完整报告、userId 或审批结果。Python 经现有内部客户端转发 Java。

Java 内部创建为 `POST /internal/order/aftersales/create`，JSON `sourceMessageId/report`，必须同时提供有效内部令牌和真实登录会话。Java 再查询当前用户所属订单；内部令牌不能替代业务归属校验。此接口没有前端创建报告的公共路由。

用户案件前缀：`/api/order/aftersalesCase`，经 Gateway 重写至 `/order/aftersalesCase`：

| 路径 | 参数/作用 |
|---|---|
| `/list` | page/size/state；只列本人案件，单页最多 50 |
| `/detail` | caseId；本人案件、全部方案版本、任务及时间线 |
| `/confirm` | 当前版本用户确认；按服务端风险流转 |
| `/resubmit` | 仅已驳回案件，必须说明；生成新版本待确认 |
| `/archive` | 仅本人已处理或已驳回案件 |

状态命令使用 JSON：

```json
{
  "caseId": "<案件UUID>",
  "expectedVersion": 1,
  "requestId": "<本次操作UUID；重试保持不变>",
  "note": "<补充说明、驳回原因或人工结果>"
}
```

### 管理员入口

前缀 `/admin-api/aftersalesCase`，重写至 `/admin/aftersalesCase`。所有方法均在服务端通过原管理员 Cookie/Header 和 Redis 管理员会话鉴权，不信任 JSON 角色。

- `/list`、`/detail`：查看待审核、待处理和历史案件。
- `/approve`、`/reject`：批准进入人工任务，或记录驳回理由。
- `/claim`：登记当前管理员为实际处理人及领取时间。
- `/succeed`、`/fail`：当前领取人填写结果，失败必须有原因。
- `/retry`：失败后人工重开任务，增加 attempt 并保留旧结果。
- `/archive`：仅允许已处理/已驳回案件归档。

案件响应包含 caseId/orderId/state/version/planVersion/risk、诊断快照、plans/tasks/timeline、源消息和创建/更新时间，始终包含 `executionAllowed=false`。人工任务记录处理人、开始/结束时间和结果说明。

## 七、LangGraph 接入与运行开关

原分支增加：`diagnosis_analyze → case_record → finalize`。MCP 继续负责原订单/物流只读工具，RAG 不重写。

`AFTERSALES_CASES_AUTO_CREATE` 默认为 false：返回 ON_REQUEST 和按消息建案入口，不自动访问新表，避免尚未授权迁移的环境破坏原诊断。此时显式建案 API 在完成迁移后可使用，不要求开启自动模式。

审核、迁移和部署后如需自动建案，可通过受控启动环境设置 true；模型和普通请求不能修改该配置。有效订单诊断会调用 Java 创建 AWAITING_USER 案件，不自动确认或审批。订单不可验证则 INELIGIBLE；建案失败为 UNAVAILABLE，保留诊断并提示按已保存消息重试，不宣称建案成功。

案件引用保存于原 `bizData.aftersalesDiagnosis.caseWorkflow`，正文也显示案件号或未保存状态。没有生成 pending action/actionId，不进入原 confirmAction 执行器。

Python 消息保存与 Java 案件是两个服务事务，不宣称分布式原子提交；超时后可能已经建案，因此重试使用相同消息幂等。若建案后消息落库失败，可从本人案件列表查找，不能通过覆盖已存在诊断解决。

## 八、安全边界

1. 当前用户来自既有登录上下文；Python 从本人已完成消息读报告，Java 再验证订单归属。
2. 本人案件检查在 Java 服务中执行，含查询、确认、重新提交、归档与请求重放；不能凭案件 UUID 越权。
3. 管理员身份来自 Redis 管理员会话的账户；不能用普通用户 Token、请求 admin=true、伪造 handler 或 userId 提权。
4. 风险白名单与状态机在后端；旧版本、非法跳转、并发和幂等号复用均会拒绝。
5. 通过审批只创建人工任务，领取/结果只是记录人工工作；不存在案件退款执行接口、自动执行器、Pay/Refund 客户端或自动退款 MQ 消费者。
6. 原 Agent 退款服务端隔离与 Java 订单归属实现未修改；原相关 Python/Java 回归通过。请求 executeRefund=true 不会增加任何权限或触发退款。
7. 审计记录业务操作者账户/用户 ID，不存请求头 Token 或 API Key。处理说明和诊断快照仍是业务数据，按本人/管理员权限读取。
