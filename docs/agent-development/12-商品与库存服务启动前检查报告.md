## 8. Search 是否必须恢复及索引/模型副作用

### 8.1 MCP 商品工具的真实调用链

```text
SEARCH_PRODUCTS
 → MCP handler → mcp_tools_service.tool_search_products
 → ProductService.search_products
 → RagRetriever.search_product_keyword_ids（直接 HTTP 查 ES simlect-index）
 → RagRetriever.search_product_vector_ids
    → _vector_search → embed_text → 配置的 /embeddings → ES向量索引只读检索
 → RRF → JavaInternalClient.snapshot_batch / search_on_sale
 → Gateway /internal/product/** → Product
 → 结构化商品结果/卡片

GET_PRODUCT_DETAIL
 → MCP → ProductService.get_product_detail_text
 → Gateway /internal/product/agent/getDetail → Product
```

Python 两个工具**没有同步调用 simlect-search 的上述必经步骤**；因此在只验证同步商品/库存读链路时，不必强制恢复 Java Search。

但当前普通 SEARCH_PRODUCTS 会尝试向量召回，`embed_text` 在查询向量索引前就可能请求外部 Embedding；**向量索引为空或 Java Search 未启动，都不能证明不会发生模型请求。** 本轮没有调用工具。下一轮未经授权不能直接用真实聊天/MCP搜索做冒烟测试，应先使用现有测试中的 FakeLLM/Mock Embedding 或单独测试 Java 只读接口；不能虚构已有“关闭 Embedding”环境开关。

### 8.3 如果恢复 Java Search，会发生什么

- EsSearchComponent.createIndexWithIK 的 PostConstruct 检查关键词索引：存在则跳过；缺失才尝试 createWithMapping。不是无条件重建，但确实可能写索引结构。
- Search application.yml 的 VectorStore initialize-schema=true，启动可能进行向量索引/映射初始化；本轮不执行。
- RabbitMQRagListenerComponent 和 RabbitMQRagDeadListenerComponent 有 RabbitListener，启动正常自动配置后会注册消费者。主队列处理可能通过 ProductFeignSupport 拉商品，再调用 VectorStore.add/delete，导致向量变化及潜在真实 Embedding。
- 本轮读取 rag.queue/rag.dead.queue：messages_ready=0、messages_unacknowledged=0、consumers=0。这仅是当时快照，不是对启动后永远不会收到消息的承诺。
- 普通商城 `/api/search/**` 及商品变更索引/向量维护需要 Java Search 对应功能；如果验收要覆盖这些，应在隔离、索引保护和模型授权审查后单独恢复。
- 不调用 SearchToolInternalController 的 productData/ragData 做“健康检查”：它们会写索引或发送消息。

**本轮结论：暂不恢复 Search。** 当前关键词索引可作为后续只读/Mock 搜索验证的现有数据源；向量0条和外部模型权限问题需单独列为尚未验证，不能伪装成完整语义搜索成功。
