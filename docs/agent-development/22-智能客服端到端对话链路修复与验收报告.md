## 1. 结论与实际根因

已完成代码修复、Mock/单元回归、真实 DeepSeek 兼容验证和三模式 HTTP/WebSocket 运行验收。消息20、21、22均产生持久化回复，收到对应 messageId 的 WebSocket DONE；Supervisor 复合任务实际调用了两个专业工作流。浏览器画面验收受工具限制而未完成，不能声称已经人工看到聊天窗口展示。

### 已证实的问题

1. **sendMessage 是异步受理接口，不是同步答案接口。** 原消息15的数据库状态已为2，助手回复长度为1909字节，并非任务未启动或未落库。因此未将接口改成同步阻塞。
2. **前端缺少持久化结果兜底。** 新消息只依赖 WebSocket。极快完成事件可能先于 HTTP 受理响应；此时列表尚未建立该 messageId，事件无法匹配。断线、页面重挂载也可能丢失通知。原历史加载不会持续同步最新消息，用户可能一直等待。这是代码中可复现的竞态；未声称已追溯证明消息15当时确实丢失了哪一个网络帧。
3. **泛导购要求被错误当作商品名过滤。** “搜索当前商城实际在售的商品”“推荐适合日常使用的商品”等整句被存入 keyword。真实商品及SKU已查询成功，但名称匹配将候选全部排除，旧消息14—16均出现“没有同时满足条件的可推荐SKU”。
4. **错误通知可能阻断终态落库。** 原异常/繁忙处理先发 Pub/Sub，再保存回复；通知失败会使持久化代码无法执行。后台任务也缺少显式强引用集合和总执行超时。
5. **真实 DeepSeek 结构化协议不兼容。** 普通 `deepseek-flash` 调用成功，但原结构化提取返回400。供应商脱敏错误为：`Thinking mode does not support this tool_choice`。原代码捕获后返回规则解析，不能把该降级当成真实模型提取成功。

### 未发现的问题

三模式分派原本存在；当前用户身份经服务器验证并传递至子任务，未发现 sendMessage 中伪造 userId 的入口。原运行消息及本轮实测均可落库。未发现需要重写 Java Agent Controller、RabbitMQ 投递或同步返回答案的依据。

## 2. 原有架构与修复后的链路

实际执行入口是 Python FastAPI。商城 Vite 对 `/api/agent` 单独代理至7050，其他 `/api` 代理至 Gateway 8080；Gateway 本身也提供 `/api/agent/**` 到 Python 的路由。

```text
前端 POST /api/agent/sendMessage
  → Vite7050代理（或Gateway8080代理）
  → FastAPI agent.send_message / 可信登录上下文
  → AgentOrchestrator：保存用户消息，返回messageId
  → asyncio后台任务（强引用、总超时、异常终态）
  → AgentEngine按 support / shopping / supervisor 分派
  → 独立LangGraph；Supervisor调用两个原专业工作流
  → DeepSeek需求理解（导购） / 售后确定性诊断
  → MCP真实HTTP工具调用
  → Gateway → Java Product / Stock / Order等业务接口
  → 结构化真实事实，保留价格/库存未知和政策不确定性
  → MySQL agent_message保存最终回复
  → Redis Pub/Sub → Python WebSocket → 前端
  → 前端按messageId查询本人持久化结果兜底
```

聊天任务不通过 RabbitMQ 调度；RabbitMQ 仍用于项目其他业务。Java负责网关、身份/业务接口、商品库存及订单事实，不负责此版本聊天消息表的写回。因此本轮 Java sendMessage Controller、AI回复查询、异步任务状态等测试项目不适用；对应功能在 Python 测试与真实 Gateway 代理验证中覆盖，未虚构 Java Agent 测试。

售后诊断节点保留代码驱动的事实/政策融合，不为证明“调用模型”而让模型重新生成价格、库存或政策。DeepSeek负责导购需求理解；商品建议由经过校验的业务数据组织。
