分析日期：2026-11-02，Asia/Shanghai。项目根目录：`E:\Simlect-AI-Mall-main\Simlect-AI-Mall-main`。

**本报告是待审核的增量实施方案，不是完成报告。没有修改业务源码、.env、数据库结构或 Gateway 配置，没有重启服务、运行测试、调用真实模型/Embedding、执行支付/退款或提交 Git。** 所有“拟新增”接口、文件及字段均是设计，不是现有能力。

## 1. 结论及实施边界

建议保留现有前端聊天、Agent 编排、LangGraph、MCP、Gateway、ES 召回和 Java 商品/库存服务，在以下位置修补：

1. Java Agent 专用商品读层补齐 SKU、价格/状态来源与严格库存结果，复用现有 Mapper 和库存 Feign。
2. 商品专用结构化结果贯通 MCP、Python 解析、咨询快照及 Agent 卡片，区分空结果、不可售、库存未知和服务故障。
3. 商品事实回答由服务端根据本轮可信数据组装；在事实校验之前不推送模型原始流式内容。
4. 只修改 Agent 商品卡片的未知状态展示，不改变商城购物详情、下单、库存变更、退款或订单归属逻辑。

不建议重写图、MCP Server 或商品服务，不新增数据库/索引/缓存中间件，不让 Python 跨库查询库存，不增加 Gateway `/internal/**` 通配放行，不将这次工作扩成售后 RAG 或复杂售后工作流。

## 3. 十个关键技术问题的源码答案

### 3.1 当前采用什么搜索，是否使用 ES？

是混合搜索，并非只调 ProductAgentInternalController：

- `app/rag/retriever.py::search_product_keyword_ids` 搜索 `simlect-index`，使用 productName match + productName.keyword wildcard；返回商品 ID。输入通配符已转义。
- `search_product_vector_ids` 通过 `_vector_search` 查 settings.es_index 的 content_vector，metadata.dataType=product；兼容尝试 vector 字段。
- `app/rag/embedding.py::embed_text` 会请求配置的 `/embeddings`，可能调用真实外部服务；本轮未执行。
- `app/rag/rrf.py::rrf_merge` 融合排名。当前候选数 24、结果数 12、RRF_K=60。
- Java `searchOnSale` 则是 MySQL 商品名 `LIKE`、分类条件、在售状态和固定排序，最多 50 条。ES 异常时存在 Java 关键词兜底；但熔断直接返回空列表的路径不等同于异常兜底路径。

### 3.2 价格从哪里读取？

- SPU 范围价来自 `simlect_product.product_info.min_price/max_price`，SQL 类型 decimal(10,2)。
- SKU 售价来自 `simlect_product.product_sku.price`，同为 decimal(10,2)。
- `ProductInfoServiceImpl.saveProduct` 用 SKU 价格最小/最大值维护 SPU 范围价。
- 搜索索引用于召回，不应作为最终价格/库存真相；当前批量回填返回 minPrice，但 ProductInfoSnapshotVO 没有 maxPrice。
- JavaInternalClient.normalize_keys 递归转 snake_case，本身能正常转换字段；不完整主要发生在 Java DTO和后续裁剪，而非该函数完全不会解析。

### 3.3 SKU 库存在哪里，能否实时查？

对照仓库 `sql/02_product.sql`、`sql/03_stock.sql` 和当前 Mapper：

| 数据 | 表/键 | 关键事实 |
|---|---|---|
| 商品名、状态、范围价 | simlect_product.product_info，product_id | status=-1 删除、0 下架、1 上架 |
| SKU、价格、规格组合 | simlect_product.product_sku，主键(product_id, property_value_id_hash) | **没有 stock 列**，也没有独立数字 skuId 列 |
| 规格名称/值 | product_property_value，主键(product_id, property_value_id) | SKU 的 property_value_ids 用 `-` 分隔并关联此表 |
| SKU 库存 | simlect_stock.sku_stock，主键(product_id, property_value_id_hash) | stock 非空整数，是库存服务的数据源 |

本轮核对的是仓库 DDL、实体、Mapper，没有在线执行 DDL 或查询业务库存数据；不将其冒称为当前每行数据一致性的证明。

已有 `StockFeignClient`、`StockFeignSupport`、`StockInternalController`、`SkuStockService`。`/internal/stock/get` 经 Mapper.selectByKey 查询库存库，能够按查询时点读取当前数据库库存。不是预占库存或交易锁定承诺，下单仍须走原业务校验。

Feign 使用 `@FeignClient(name="simlect-stock", path="/internal/stock")` 的服务发现路径；没有指定必须经 Gateway 的 URL。源码注释中“Feign → Gateway”的描述不能代替真实注解。Gateway 当前没有 `/internal/stock/**` 专用路由，**商品服务经现有 Feign 访问库存不要求补这个路由**。

### 3.4 为什么 Agent 返回 stock=null？

- `ProductAgentInternalController.getDetail` 直接 productSkuMapper.selectList，未调用库存服务；ProductSku.stock 是未被当前 Mapper填充的临时字段，可能为 null。
- `ProductInternalService.snapshotBatch` 也直接查 Mapper；ProductSkuSnapshotVO **没有 stock 字段**，不能把快照中的缺失解释为零。
- 普通商城 `ProductInfoServiceImpl.getProduct4VOByProductId` 会遍历 SKU 调 `StockFeignSupport.getAvailable`，后台 SKU 列表也有类似补齐。Agent 专用路径绕过了这些步骤。

### 3.5 现有库存读接口能否直接保证“未知不当零”？

不能完全保证：

- StockFeignFallbackFactory 返回不可用响应，FeignResponseSupport 对非 200/传输异常抛 BusinessException；**服务不可用并非所有路径都被默认成零**。
- 但 SkuStockService.getStock 在记录不存在时返回 stock=0；现有测试 `getStock_rowNotFound_returnsZeroStock` 固定了此旧契约。
- StockFeignSupport.getAvailable 在成功响应的 data=null 或 stock=null 时也返回 0。
- totalByProduct 同样存在 null→0；总库存为零不能证明目标 SKU 有真实库存记录。

因此“捕获异常置 null，然后调用旧 int getAvailable”仍不足以严格区分记录缺失与真实零库存。不能为 Agent 改坏下单等共享调用的旧行为。

### 3.6 下架、删除、缺货如何处理？

- Java searchOnSale 只查询 status=1；批量快照包含状态，Python `_load_products_by_ids` 过滤明确非在售，但 **status 缺失时仍允许通过**。
- getDetail 读取商品后返回状态，不主动隐藏删除行；Python get_product_detail_text 将所有非 1 都叫“已下架”，混淆删除、下架和未知状态。
- `ProductInfoServiceImpl.deleteProduct` 使用 status=-1 软删除，并通过原消息路径同步检索数据；ES 与 MySQL 可能存在同步时间差，必须回源确认。
- 当前 Agent 没有可靠的完整 SKU 库存结果，不能证明它能正确区分缺货和库存服务异常。

### 3.7 MCP 是否有统一结构？

部分有：`ToolInvokeResult` 与 `SIMLECT_TOOL_RESULT:{json}` Wire 支持 content、assistantCards、bizType/bizData、productIds/productNames 等。

但详情工具现在返回纯文本，结构中没有明确 queryStatus、库存状态、查询时间或逐字段来源；to_tool_message 只给 LLM content，to_biz_dict 主要是 ID/名称。`parse_tool_wire` 接受普通文本、坏 JSON 时也退回文本。mcp_streamable_client 的 isError/超时会变成普通失败文本；router 在解析前就计 success，且搜索还可能本地再跑并覆盖错误。需要商品分支可靠判定，不将“收到文本”视为业务成功；本轮不扩展成全工具可观测性重构。

### 3.8 Python 在哪里丢失或误解数据？

- get_product_detail_text 仅输出名称、ID、范围价、销量和短描述，**丢掉已经拿到的 skus/property_values**。
- `_load_products_by_ids` 对批量快照仅取 products，忽略同响应顶层 skus/property_values；批量请求抛异常并不会进入其所谓逐个详情 fallback（该分支只检查空/结构）。
- `product_snapshot_service` 在两个组装分支使用 `stock or 0` 汇总缺失库存，并推导 inStock=false；结构化详情分支只取 properties，不能自动等同于 Java 返回的 property_values。
- 快照可从 Redis 或前端卡片回退，缺少强制刷新时间约束；前端商品卡价格不能充当当前事实。
- build_product_payload 只保留 ID、名称、封面、最低价，且 `min_price or minPrice` 会误处理合法的数字 0。
- AgentProductList.vue 的 `Number(val ?? 0).toFixed(2)` 会把未知价格显示为 ¥0.00。前端也需要商品客服组件内的小范围修正。
- 可选 DB 适配器 java_internal_client_db 的 snapshot_batch/get_product_detail 仍 SELECT product_sku.stock，与当前分库 DDL 不符。当前配置为 http，该问题属于兼容风险，不能靠新增 Python 跨库 SQL来修复。

### 3.9 模型是否可能编造价格/库存？

仍可能。现有 Prompt 有真实数据约束，product_text_guard 主要检查卡片/文案一致性，并不是逐值事实校验器。

`agent_runtime.stream_llm_turn` 会在最终检查前立即 push_chunk。nodes 对部分强制工具分支已有非流式处理，但普通商品咨询路径仍可先发送模型内容。只在 finalize 改文案或只加 Prompt，不能撤回已经显示的虚构库存。

post_turn、取消/异常分支还会使用 chunks 处理记忆或部分消息，方案也必须避免将未验证的商品事实存入历史，下一轮再被当作真相。

### 3.10 会不会影响普通商城？

若直接修改 ProductInfoServiceImpl.getProduct4VOByProductId、旧 StockFeignSupport.getAvailable 或共享快照契约，存在购物、下单和订单依赖回归风险。

推荐把新聚合逻辑限定为 Agent 专用服务和增量只读接口；保留上述原契约及库存写操作。普通商城依然按原入口工作，并做 Mock 兼容回归。

## 4. 问题与修复优先级

| 优先级 | 已确认问题 | 计划处理 |
|---|---|---|
| P0 | 缺失库存被汇总为 0；前端未知价格显示 0.00 | nullable 数值 + 独立状态；禁用 `or 0`/未知价补零 |
| P0 | 未校验的模型商品事实先流式输出 | 商品事实回合先取证、缓冲、服务端事实渲染；覆盖取消/异常/记忆路径 |
| P0 | 现有库存读契约无法区分缺行/真零 | 增量严格只读批量库存契约，保留旧 getStock 行为 |
| P1 | Agent Java 入口不补库存，SKU 被裁剪 | Agent 聚合服务回源 SKU/规格并调用现有库存 Feign |
| P1 | 异常/空列表/不相关热销兜底混合 | 类型化状态，显式区分召回结果、另荐商品和下游失败 |
| P1 | 搜索远程+本地重复执行、错误可被覆盖 | 产品分支仅一次权威召回；旧成功结果按 ID补齐，不重跑 Embedding |
| P1 | status 缺失放行、删除/下架混淆 | 搜索只放行明确 ON_SALE；详情明确状态与不可售原因 |
| P2 | DB 兼容适配器、共享快照缺字段 | 明确能力状态，库存未知不伪装成功；不重构订单/旧部署 |

## 5. 推荐增量架构

### 5.1 Java Agent 专用商品聚合

拟新增 `ProductAgentQueryService`，复用 ProductInfoMapper/ProductSkuMapper/ProductPropertyValueMapper 的参数化查询。聚合名称、上下架、SPU 范围价、SKU 价格、规格，并经库存 Feign 取得严格库存结果。

拟为 `/internal/product/agent/` 增加一个批量事实查询入口（建议名 `/queryBatch`，**尚不存在**）。ES 只负责 ID 排序，分类/热销/MySQL搜索也只负责候选；**最终所有卡片和详情均经同一个聚合器回源**，不能只有混合搜索才补齐库存。

现有 searchOnSale 保留 List 响应；新批量事实接口接受有界 ID 列表。getDetail 在保持原 productId/productName/minPrice/maxPrice/status/skus/propertyValues 等字段兼容的基础上，委托聚合器并补充状态，不改变普通商城详情或共享 snapshotBatch。

Mapper 和数据表优先原样复用；Agent 新接口不跨库 JOIN，商品库存仅通过库存服务获取。无需改数据库结构或 ES 索引。

### 5.2 严格只读库存契约的必要增量

推荐增加 `/internal/stock/queryBatch`（**拟新增**），沿用 StockFeignClient 和内部令牌认证，只读取 sku_stock，结果按复合键返回：

- FOUND：该行存在且 stock 为合法非负整数，允许 stock=0。
- MISSING：该行不存在，stock=null，不借用旧 getStock 的“缺行即零”。
- 传输/服务/响应错误：由商品聚合器转成 UNAVAILABLE/INVALID_RESPONSE，stock=null。

新严格读方法还需检查 ResponseVO 的 status/code 是否一致表示成功，以及 data、键和数值是否合法；不能因为旧 FeignResponseSupport 只检查 code，就把 status=error/code=200 的矛盾响应当成成功。此检查限定新增读方法，不改变全站共享拆包契约。

为此在原 SkuStockService/Mapper 增加批量 SELECT 和读 DTO，在 StockFeignClient/Support/FallbackFactory 增加对应方法。旧 get/getAvailable/totalByProduct/lock/change/set 等签名和语义不变；不新增库存数据库或并行库存计算逻辑。

批量 SELECT 使用参数占位并校验数量、去重复合键；只读查询不调用 FOR UPDATE、预占或扣减方法。此增量是为区分缺行与真零、避免逐商品逐 SKU N+1，不是另造库存服务。

### 5.3 控制调用规模

- 复用现有召回数 24/输出数 12，初版不扩大搜索量。
- 批量商品 ID 建议上限 50、单批库存键建议上限 200，具体常量在实现测试时固化；这些是设计上限，不是现有参数。
- SKU 过多时明确分页/截断与 skuComplete=false，不把部分 SKU 的合计当成商品总库存。
- 对单次查询设整体超时预算；禁止远程搜索后无条件再跑同一搜索，禁止每条卡片重复触发 Embedding。
- 当前查库存是时点数据，返回 observedAt；页面展示不构成最终成交价、库存锁定或下单成功保证。

## 6. 数据结构设计（拟定 schemaVersion=2）

Java 继续使用原 ResponseVO 外层，商品专用结果放在 data/工具扩展字段内；Python 统一规范 snake_case，Wire/前端维持 camelCase。现有卡片四字段和 PRODUCT_SEARCH_RESULT 外形保留，新增字段可选，避免破坏历史消息。

示例为**契约示意，不是真实商品或测试结果**：

约束：

- skuId 使用真实 property_value_id_hash，只有结合 productId 才能标识 SKU；不虚构数据库不存在的单字段数字主键。skuName 只从商品自身规格关联生成，缺关联则明确规格不完整。
- 金额使用十进制字符串/Decimal，保留合法零价；未知为 null/UNKNOWN，不使用 float 计算权威价格。兼容旧 minPrice 字段时只做展示转换。
- SPU 范围价和 SKU 价注明不同表来源；发现不一致则标 PRICE_INCONSISTENT/待确认，不让 Python/LLM选择一个自认为正确的价格，也不在查询时修库。
- stockQueryStatus：SUCCESS、UNAVAILABLE、MISSING、INVALID_RESPONSE、NOT_REQUESTED；只有 SUCCESS 才允许给出数量。stock=0 是有效数值，不是失败哨兵。
- availability 与查询状态分开：IN_STOCK、OUT_OF_STOCK、UNKNOWN、NOT_FOR_SALE。
- 所有 SKU 都已完整成功查询时才给 totalStock；任一缺失/失败/截断则 totalStock=null，保留各 SKU 已知结果，不把未知项按零求和。
- queryTime 为服务端本次响应时间；productObservedAt/stockObservedAt 为各自实际查询时间。缓存数据保留原时间和来源，不能换成“现在”后冒称实时。
- sources 区分召回来源与业务事实来源：ES 命中并不意味着其价格/库存可直接展示。

## 7. 状态与异常处理矩阵

| 场景 | 结果语义 | 数值与展示 |
|---|---|---|
| 在售、库存行存在且 >0 | SUCCESS/OK，stock SUCCESS，IN_STOCK | 显示真实 SKU 价/库存与时间 |
| 库存行存在且=0 | SUCCESS/OK，stock SUCCESS，OUT_OF_STOCK | 明确缺货；不能隐藏成查询失败 |
| 搜索成功但无相关候选 | SUCCESS/NO_MATCH | products=[]；不等同于“系统不存在任何该商品” |
| 指定 ID 不存在 | SUCCESS/PRODUCT_NOT_FOUND | 不返回商品事实，不自动换另一商品 |
| status=0 | SUCCESS/PRODUCT_OFF_SALE | 不作可购买推荐，不补造库存 |
| status=-1 | SUCCESS/PRODUCT_DELETED | 返回最小不可售状态；不泄露删除商品详细规格/描述 |
| 状态缺失/非法 | PARTIAL/PRODUCT_STATE_UNKNOWN | 搜索不当在售；不能默认上架 |
| 库存服务超时/不可用 | PARTIAL/STOCK_UNAVAILABLE | 商品基础事实可保留，库存=null/UNKNOWN，明确无法确认 |
| 库存行缺失 | PARTIAL/STOCK_RECORD_MISSING | 库存=null，不沿用旧缺行=0 |
| 库存返回 data=null/stock=null、错键或负数 | PARTIAL/INVALID_STOCK_RESPONSE | 库存=null，不当成功、不截成零 |
| 商品服务/DB失败 | ERROR/PRODUCT_SERVICE_ERROR | 无权威商品事实；返回失败，不能说“没搜到”或偷偷热销冒充成功 |
| ES/Embedding失败、MySQL关键词兜底成功 | 依据最终召回完整性返回 SUCCESS 或 PARTIAL，保留召回告警 | 明确关键词结果，不能夸称语义搜索全部完成 |
| 所有召回不可用/熔断 | ERROR/SEARCH_UNAVAILABLE | 不返回“商品不存在” |
| 部分商品/SKU查询失败 | PARTIAL | 已知数据与未知分开；合计不伪造完整 |

关键词无匹配但用户允许推荐时，另荐商品放 alternatives，带“非搜索命中”来源；不把 source 改成 hybrid，不覆盖失败/空结果状态。服务故障不能通过热销兜底包装成原查询成功。

## 8. Python、MCP、快照与输出的具体改造

1. 增加轻量 ProductQueryResult 类型，校验 schema、状态、价格/库存与商品/SKU复合键。保留 JavaInternalClient 的 ResponseVO 拆包、HTTP 错误处理和键名规范化，不重写客户端。

3. 对商品召回增加类型化状态与兼容旧 list-ID 包装器，避免 retriever 吞掉异常后无法分辨空结果。仅限定商品分支；FAQ/售后检索旧返回和工作流保持兼容，不在本轮开发政策 RAG。

5. SEARCH_PRODUCTS/GET_PRODUCT_DETAIL 名称和输入 schema 保留；详情业务函数改成返回统一结果，由现有 MCP `_text` 复用序列化。普通文本失败、坏 Wire 不准升级成“成功空商品”。

8. 复用 tool_biz 传递商品事实证据，不另造 LangGraph 流程。商品事实问题若缺 ID则追问或查询；若已有商品 ID则强制调用只读详情，而不是让模型跳过查询。
9. 商品事实回合采用缓冲/现有非流式模式，事实字段由服务端模板根据权威结果生成。不能只加 Prompt或数字正则；不能先把原始 LLM chunk 发出再修正。模型可以辅助理解意图，但不负责补全名称、金额、规格、库存、可售状态。
10. final、取消、异常和 post_turn 记忆路径共同使用经过校验的输出；未经验证的模型事实既不推送，也不作为部分消息或“可信快照”持久化。
11. AgentProductList/ConsultProductCard 对 null 价格显示“价格待确认”，库存按成功/缺货/未知/不可售显示。只改客服组件，不改普通商品详情、购物车和结算 UI。

## 10. 安全与兼容性

- 沿用当前登录上下文、工具白名单、服务内部 Token；模型的 userId 仍被覆盖，保留订单归属校验。商品 ID只作参数化查询，不接受模型指定数据源、状态或库存值。
- SEARCH_PRODUCTS 还会读取该 userId 的 Redis 咨询上下文与浏览记录。当前 MCP 商品 handler 未像订单 handler 一样使用 `_verified_order_user` 包装，不能仅因是商品只读工具就忽略直接 MCP 请求伪造 userId 的风险。实施时应在商品搜索入口复用现有基于 HTTP token 的用户校验/ContextVar 绑定，并在读取个性化上下文前再次约束已认证用户；保持订单验证器原逻辑不变。公共商品事实本身不引入订单归属规则，但个性化数据不能任意指定用户。
- 库存新增接口只读，不暴露 change/set/lock 工具；只取 SKU_key 对应本商品的记录，拒绝错配响应。
- 不改 AGENT 退款隔离策略、action_execute_service、pending 确认边界或 Java 商城正常退款入口。
- 对数据库商品名称/描述也当不可信文本，JSON/HTML 安全编码，不允许内容伪装成模型系统指令；来源字段由服务器写，不接受客户端/LLM自报。
- 金额、库存、状态、时间由服务端数据决定；缺证据就明确未知，不能用销量推算库存或从旧消息猜价格。
- 老消息、旧 MCP Wire、四字段商品卡继续可解析；未知字段不破坏订单/退款卡。兼容不意味着信任旧消息里的实时价格/库存。
- 日志只记商品/请求相关 ID、状态、耗时和错误类型；不输出用户 Token、内部令牌、API Key或原始敏感报文。

### 四、Gateway 路由与三个服务的实际调用关系

Gateway 当前已有以下路由，无需为了注册诊断修改：

| 路径 | 目标 | 作用 |
|---|---|---|
| /internal/product/** | lb://simlect-product | Agent 与 Java 内部商品接口，原样路径转发 |
| /api/product/** | lb://simlect-product | 普通商城商品查询，按原 RewritePath 去掉 /api |
| /api/stock/** | lb://simlect-stock | 当前公开 StockController 主要提供 health；不等于开放内部库存读写工具 |
| /api/search/** | lb://simlect-search | 商城 Java SearchController 的搜索路径 |

同时存在相关后台商品/搜索路由。没有 `/internal/stock/**` 通配转发，但当前 Java 库存 Feign 用服务名发现直连目标，不要求新增该 Gateway 路由。

实际关系：

```text
Python Agent 商品同步查询：
  ES 关键词 / 商品向量召回
  → Gateway /internal/product/** → simlect-product → 商品 MySQL
  → 增强后 Agent 商品聚合复用 StockFeignClient
  → Nacos 发现 simlect-stock → /internal/stock/get 或拟新增严格读接口
  → 库存 MySQL

普通商城详情：
  Gateway /api/product/** → simlect-product
  → ProductInfoServiceImpl.getProduct4VOByProductId
  → StockFeignSupport → simlect-stock

普通商城 Java 搜索与索引维护：
  Gateway /api/search/** → simlect-search → ES
  Search 的 ProductFeignSupport → simlect-product 获取商品索引数据
  商品变更消息 → RabbitMQ → Search 的 RabbitMQRagListenerComponent
  → ProductFeignSupport.getRagIndex → 向量内容处理 / VectorStore
```

依据文件：StockFeignClient、ProductFeignClient 的 `@FeignClient(name=...)`，ProductInfoServiceImpl、SkuStockService、Search 的 EsSearchComponent、RabbitMQRagListenerComponent、SearchToolInternalController。

库存读取本身的 `SkuStockService.getStock` 只查库存 Mapper；虽然库存模块也依赖 product-api 并启用 Feign，不能据此声称每次读库存都会调用商品服务，更不能声称库存必须经 Java Search。

**Java simlect-search 不在每次 Python Agent 搜索的同步必经链上。** Agent 可以直接读既有 ES 索引并向商品服务回源；但索引更新、向量同步及普通商城 `/api/search/**` 的可用性又依赖 Java Search 的对应功能，应分别验收，不能一概说 Search 必须启动或完全不需要。
