## 1. 结论分级

### 已确认事实；尚无已证实的直接根因

- Order PID 35400、Agent PID 32412、MCP PID 7372 已不存在；Gateway PID 16884 仍存活且健康。
- 三者是本机 Windows 后台进程，不是 Docker 容器，也没有发现对应 Windows 服务。它们通过同一组启动脚本创建，但不是同一次 PowerShell 调用：Order 单独执行 Java Stage；MCP/Agent 由另一次 Python Stage 依次启动。
- 未发现三个应用的致命崩溃/OOM 堆栈或正常停机完成日志；没有可用退出码和精确进程终止时间。
- 18:49 的进程核验确认三个正常 PID 仍存活；Order 随后持续输出到 20:36:43。因此 18:48 的隔离夹具清理不是这三个正常进程立即退出的原因。
- 本聊天在 20:56:59.858 有明确 turn_aborted 事件；20:58 的收尾检查确认三个服务已不可用。中断发生与发现故障之间存在时间关联，但不是 Windows 进程终止证据。
- MySQL、Redis、ES、RabbitMQ、Nacos、Gateway 当前可用；中间件容器没有在这个窗口重启、退出或 OOMKilled 的证据。

### 高概率原因

**外部执行宿主/任务生命周期终止，比三个应用独立业务崩溃更符合现有证据。** 具体候选是 Codex 任务中断时的进程树/执行环境回收、控制台或 Job Object 生命周期结束。

依据：三个本轮由工具启动的新进程消失，较早启动的 Gateway 保持同一 PID；应用未记录正常停机或致命异常；依赖保持运行；存在 20:56:59 的任务中断事件。

此结论仅是当前优先排查假设。**没有捕获 TerminateJobObject、TerminateProcess、控制台关闭事件或内核终止记录，不能确认具体终止 API，也不能断言 Codex 一定终止了三个进程。**

### 尚无法确定

- 三者是否在同一秒退出，以及具体退出码。
- 是否存在人工结束进程、外部管理程序回收、终端关闭或资源压力参与。
- 是否被纳入设置了 KILL_ON_JOB_CLOSE 的 Windows Job Object；当前已无法检查这三个已消失进程的对象成员关系。
- 是否有未写入日志的原生崩溃或瞬时依赖故障。现有日志和事件不支持这些假设，但不能证明绝不发生。

## 8. 建议恢复方式（仅建议，未执行）

1. 审核本报告后，先选择不随临时任务生命周期结束的进程管理方式：用户持有的独立终端，或后续经批准设置专门的 Windows 服务/持久任务管理器。不要仅依赖临时工具进程和一次性 PassThru 对象。

4. 启动后用只读健康检查及持续观察验证存活；特别跨越启动脚本退出、聊天任务结束这两个时点观察。若要验证中断影响，应仅使用无业务能力的测试进程，不能用正常服务做破坏性实验。
5. 不因当前证据不足而改退款/订单代码，不凭低内存余量直接认定需要扩大 JVM、删除数据或重启全部服务。
