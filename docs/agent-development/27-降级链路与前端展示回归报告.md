## 修复后的保存顺序与数据契约

原顺序：push_done → 数据库写入 → 异常时push_chat_error → 丢弃biz_data并补写status2。现在为：严格序列化 → 同一SQL原子保存text+biz_data+status2 → 推DONE（携带bizData）。失败则抛MessagePersistenceError，经独立分支写入status4/agent_persistence_error并推DB_PERSISTENCE_FAILED；不走原无证据成功补写，不运行后处理摘要。

政策biz_data保留原有status/hits字段全部内容，增加kind=policy_answer、messageId、responseStatus、modelStatus、modelFailureCode、executionAllowed=false。模型正常返回为SUCCESS；模型超时/503为DEGRADED，政策原文照常保存；RAG无依据为EVIDENCE_UNAVAILABLE。HTTP200但模型JSON非法不能被当作成功。

如果WS发布失败但数据库已经成功，不反向改成失败或丢弃证据，前端通过同一messageId的所有者范围查询恢复。取消/终态保护返回False，不发新的DONE；失败状态4不被重复完成覆盖。数据库完全不可用时只能通知明确失败，不能保证写下失败标记，不会伪称成功。

## 前端显示与关联保护

- 正常政策回答：展示答复正文，并可展开所有政策来源。
- 模型超时或503：显示明确模型超时/繁忙提示，同时正常展示已保存法规原文；不会统一替换成“服务不可用”。
- 完整证据包含文档名称、documentId、chunkId、版本、section、完整text、source、发布机构及官方URL；不截断长JSON/条款。新折叠区不依赖Redis短期Supervisor结果，直接使用该消息持久化bizData。
- 数据库失败：WS errorCode=DB_PERSISTENCE_FAILED、消息status4；文本明确“回复和证据未能完整保存”，不能被finishAnswering强行变成status2。
- 轮询getMessage能恢复status4和相同错误码；bizData按完整JSON读入，校验messageId防止串到另一条消息。其他用户仍受已有后端所有者查询限制，未信任模型的userId。
- 官方URL仅接受https，Vue文本绑定转义条款内容；没有执行证据中的指令，未增加动作确认或金融入口。

实际AgentChatItem SSR测试验证长正文末尾标记仍存在、完整Chunk/版本/来源URL展示，以及数据库错误文案。为隔离浏览器依赖，测试使用内存路由、明确标注TEST ONLY的数据和网络禁用；不把SSR结果说成商城已生成一条真实回复。Node解析/WS/轮询合同27项、类型检查、生产构建均通过。

## 异常与状态测试

政策正常、超时、503三种情况均先保存完整text+evidence，再发DONE；测试检查写入参数中包含原始全部hits且消息ID相同。数据库抛错和证据无法JSON序列化时不发DONE，图节点走独立保存失败分支，post_turn不会再调摘要。发送通道失败不会抹掉已保存数据，前端可轮询恢复。

真实MySQL临时表使用约240KB JSON（大于2000字符和65535字节）实际往返；保存前后完全相同，含来源/Chunk/版本，其他测试用户不能读到，失败状态不能被重复完成覆盖。不是只Mock一个无长度限制字典。测试适配器只替换目标表名为连接私有临时表，不改业务SQL参数或持久化实现。
