## 2. 原有调用链与缺口

退款：

```text
PROPOSE_REFUND
  → mcp_tools_service.propose_refund 查询订单/明细、检查状态
  → pending_action_service.create_pending(REFUND)
  → 前端退款确认卡
  → POST /api/agent/confirmAction
  → PendingActionService.confirm 校验提案归属并进行 CAS
  → ActionExecuteService.execute
  → JavaBridge.refund_order
  → Java /api/order/refundOrder
```

原链路中的提案不直接退款，但确认后可以真实执行；只有 Prompt 或按钮限制不足以阻断直接 HTTP、重复请求或内部调用。

订单：原 Python 的 get_order/get_order_item/list_order_items 只传业务 ID；Java 对应接口只按 ID 查询后返回。已有内部 Token 只证明服务身份，不能证明当前业务用户对该订单有权限。可选 `INTERNAL_READ_BACKEND=db` 同样存在只按 ID 读取的路径，因此必须同时保护，避免配置切换绕过。

## 3. 修改后的退款安全链路

```text
PROPOSE_REFUND → 查询本人订单/退款状态 → 生成退款建议/提案（保留）
  → 用户确认或直接 HTTP 请求
  → require_login + 提案归属校验
  → PendingActionService.confirm：REFUND 一律拒绝，不标记执行、不 CAS、不调用 executor

即使绕过 pending 层：ActionExecuteService.execute(REFUND) 仍拒绝
即使直接调用桥接：JavaBridge.refund_order 仍拒绝
即使直接调用 _post_form：退款路径拒绝，其他非白名单路径不允许
```

实现原理：

1. `refund_execution_policy.deny_agent_refund_execution()` 统一抛出 ValueError，提示“当前智能客服仅提供退款建议，不执行退款。请前往商城订单页按正常售后流程申请。”
2. 采用**第一阶段硬性关闭**，未增加可以恢复执行的环境变量开关。即便设置 `AGENT_REFUND_EXECUTION_ENABLED=true`，行为仍是拒绝；模型、请求参数和普通确认均不能改变策略。
3. pending 层先校验服务端提案记录的归属和状态，再识别 REFUND。请求只提供 actionToken，不能用 actionType、paramsJson 或 executionEnabled 覆盖 Redis 提案；不存在、其他用户、已处理记录分别由既有校验拒绝。
4. execute 在解析 paramsJson 之前拒绝 REFUND，畸形 JSON 或伪造动作参数不产生退款执行。
5. bridge 的退款方法不再包含发送退款 HTTP 请求的代码；通用写桥接只接受既有确认收货、评价和追评的精确路径。大小写、尾斜杠退款路径被拒绝；携带查询参数/路径变体也不能进入白名单。
6. 安全事件为 `agent_refund_execution_blocked`，仅记录 channel=agent、reason=advice_only；不记录用户 Token、actionToken、订单明细或密码。
7. 新旧退款提案均渲染为“退款建议/仅查看退款建议”，executionEnabled=false。通用前端可能仍发送确认请求，但服务端返回 success=false 和仅建议提示，不执行退款。
8. 其余 pending 动作的 CAS、防重复、删除失败处理保持原逻辑；本轮没有关闭商城正常售后入口或其他已允许的 Agent 动作。

MCP 注册清单中与退款有关的工具仍只有 PROPOSE_REFUND；没有注册真实退款执行工具。该工具仍可查询、分析条件并创建建议，不会调用 Java 退款执行接口。

## 4. 修改后的身份与订单归属链路

```text
用户 Header/Cookie Token
  → Python require_login：复用 Redis 登录会话验证
  → require_agent_login：绑定 request-local AgentUser
  → asyncio 后台任务继承上下文（凭据不进入图状态/提示词/工具参数）
  → Router：核对真实上下文，覆盖模型提供的 userId
  → MCP HTTP 头携带用户 Token + 内部服务 Token
  → MCP 订单工具：从 SDK 当前消息 HTTP 请求取 Token，再次验证会话与 userId
  → Java HTTP 头保留两种身份；body 携带 userId + orderId/orderItemId
  → Gateway：原有内部服务 Token 认证（保留）
  → Java Agent Controller：复用 ABaseController.getTokenUserInfo 校验业务登录用户
  → body userId 若与登录用户不同，直接失败
  → Service/Mapper：orderId AND userId 查询
  → 仅返回本人订单及其明细/物流/评价
```

身份边界说明：

- 内部 Token 的用途是识别调用服务，不能替代用户会话。Java 即便接收到正确内部 Token，没有有效用户 Token 仍返回登录失败；有用户 A Token 却提交 userId=B 也失败。
- userId 缺失时 Java 可以从已验证 Token 推导当前用户，不依赖客户端声明；伪造/不一致的 userId 被拒绝。
- Python ContextVar 通过作用域清理，并发用户不共享身份；后台 create_task 在已验证请求内创建时继承上下文。Token 不在 AgentUser repr 中，不写入 LangGraph checkpoint、模型提示词或工具 JSON 参数。
- MCP 的受保护订单工具不会仅凭内部令牌接受任意 userId；从每条 MCP 消息对应 HTTP 请求取得用户凭据，不依赖模型声明或全局可变用户变量。
- 订单相关客户端在缺少上下文或 userId 不一致时失败，不会发 HTTP/数据库查询。

Java 实现：

- getOrder：取得登录用户，通过新增 `getOrderInfoByOrderIdAndUserId` 同时限定两个字段，成功后才读取明细。
- getOrderItem：先取得订单项的真实 parent orderId，再查询该父订单与当前用户的归属；不能通过请求中另塞一个自己的 orderId 欺骗检查。验证完成前不返回明细字段。
- listOrderItems：先验证父订单归属，失败返回空列表，成功后才查明细。
- getLogistics/getComment：也先核对父订单归属，再调用原有用户过滤查询；不查询其他用户物流/评价数据。
- listOrders：使用已登录用户构造原查询，不相信 body 用户 ID。
- 新 Service 方法使用既有 OrderInfoQuery 的 orderId/userId 条件。已检查 `OrderInfoMapper.xml` 支持这两个 AND 条件，直接复用，**没有重复实现 Mapper、修改表结构或改写商城原查询接口**。
- 无归属资源统一返回 null/空列表，不返回订单正文，也不区分“别人的订单”和“不存在”。

直连数据库兼容模式：get_order 增加 order_id 与 user_id 联合条件；get_order_item/list_order_items JOIN order_info 并限定父订单 user_id。订单列表、物流和评价也要求已验证的当前用户上下文，查询使用绑定参数。该模式仍使用原适配器，不引入新生产数据库框架。
