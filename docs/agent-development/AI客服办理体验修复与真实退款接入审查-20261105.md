## 当前真实资金调用链审查

已有可复用路径：

- OrderController POST /order/refundOrder -> OrderInfoServiceImpl.refund/refundInLock/doRefund。
- 校验本人归属、订单与订单项状态、锁与并发更新、实付金额分摊；Redis退款单号锚点用于同单重试。
- PayFeignSupport -> PayInternalController POST /internal/pay/channel/refund -> PayInternalService.refund -> PayChannel4AliPay.refund。
- 支付宝SDK以原商户支付单号和稳定out_request_no发送退款；远端返回成功后提交本地事务，提交后库存幂等回补。
- Agent action_execute_service中退款仍在服务端阻断，HTTP确认不能解除。案件模拟退款与真实渠道独立。

### 尚不能直接接生产的缺口

1. AftersalesCaseService审批/履约与原商城资金接口尚未建立经过审核的自动执行桥接。不能将APPROVE简单绑定refundOrder，尤其已发货必须核对退货验收和办理类型。
2. 支付侧Redis标记在发送前写入，重复请求直接return，无法区分原请求仍在处理、已成功或结果未知。远端执行成功而本地响应/事务失败，必须有持久化退款记录和渠道查询对账，不能仅靠Redis7天标记判定成功。
3. 网络超时属于结果未知，不能直接宣称失败并生成新退款单号。需要按稳定原单号查询渠道退款结果及可审计的补偿流程。
4. 原商城直接退款允许已发货等状态，不代表新案件流程已完成退货验收；须确认业务审核规则，避免新桥接绕过人工审批。
5. 支付渠道SDK当前记录response.getBody()，生产接入前应收敛为白名单状态/错误码与脱敏关联ID，禁止将可能含交易信息的完整正文直接记日志。本轮未为仅做审查而改动运行中支付服务。
6. 现有notify主路径是支付回调，不能据此宣称退款通知、退款查询及对账已经实现并验收。
