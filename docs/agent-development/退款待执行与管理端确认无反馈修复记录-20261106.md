## 2. 根因与现场证据

只读查询实际数据库 `simlect_order.aftersales_case`、`aftersales_audit`：

- 原申请已确认、审核、接单，用户登记了物流。
- 多次管理员操作均为 `RETURN_LOGISTICS`，最后一次为17:02:07.401；它们没有生成 `RETURN_ACCEPT`。
- 16:43:08 的 `PREPARE_REFUND` 仅准备模拟单，状态 `PENDING`。没有 `START_MOCK_REFUND`、`COMPLETE_MOCK_REFUND`。
- 因此“待执行”是实际业务状态，不能显示成退款成功。截图中的确认框也是“登记退货物流”。
- 旧管理端提交整份履约表单，物流审计内可能含 `accepted:true`，但这不等于独立验收事件；现在物流记录只保存本动作相关字段。
- 校验错误原先出现在详情弹窗背后，缺少验收意见时容易表现为“确定无反应”；重复点击还能打开多次确认。
- 进度口语“退货进程”和部分退款查询误入新售后诊断；前端案件列表没有按明确订单收敛，容易混入其他订单。
- Python 以 JSON 请求案件列表和详情，旧 Java 接口主要接受表单参数。列表可能忽略订单范围，详情请求不兼容。
- 原订单的支付状态与售后模拟结果是不同记录。模拟成功不会把原支付订单伪装成已真实退款；订单页需要独立的售后进度入口。

只读证据：`.cache/refund-status-repair/current-case-before.json`、`current-case-latest.json`。未更改历史审计，未把旧物流记录回填为验收。
